Provisioning and Artifact Management in DevOps Architecture and CI/CD Pipelines

📅 Monday, September 14, 2026, 10:30 AM (Asia/Yangon) 🏷️ DevOps, CI/CD, Infrastructure

DevOps အခင်းအကျင်းတွင် Application တစ်ခုကို ရေးသားပြီး ရလဒ်ထွက်လာသည်မှ စတင်၍ သုံးစွဲသူများ လက်ထဲသို့ ရောက်ရှိသည်အထိ အလိုအလျောက် ပို့ဆောင်ပေးရာ၌ Provisioning နှင့် Artifact Management သည် မရှိမဖြစ် လိုအပ်သော ကျောရိုးအစိတ်အပိုင်း (၂) ခု ဖြစ်ကြပါသည်။

၁။ Provisioning ဆိုတာ ဘာလဲ (What is Provisioning?)

DevOps တွင် Provisioning ဆိုသည်မှာ အက်ပလီကေးရှင်းတစ်ခု သို့မဟုတ် ဆော့ဖ်ဝဲလ်တစ်ခု ကောင်းမွန်စွာ အလုပ်လုပ်နိုင်ရန်အတွက် လိုအပ်သော အခြေခံအဆောက်အအုံ (Infrastructure)၊ ကွန်ရက် (Network)၊ ဆာဗာ (Servers) နှင့် စနစ်သုံး ပစ္စည်းများအားလုံးကို အဆင်သင့်ဖြစ်အောင် ပြင်ဆင်၊ သတ်မှတ်၊ တည်ဆောက်ပေးသည့် လုပ်ငန်းစဉ် ဖြစ်ပါသည်။

အတိတ်ကာလတွင် System Administrator များသည် ဆာဗာစက်သစ်များကို Datacenter ထဲတွင် Manual တပ်ဆင်ခြင်း၊ OS တင်ခြင်း၊ IP သတ်မှတ်ခြင်းတို့ကို လက်ဖြင့် လုပ်ဆောင်ခဲ့ရသော်လည်း ခေတ်သစ် DevOps တွင်မူ အရာအားလုံးကို Code ရေးသား၍ Command တစ်ချက်တည်းဖြင့် စက္ကန့်ပိုင်းအတွင်း အလိုအလျောက် ပြုလုပ်ကြပါသည် (Infrastructure as Code - IaC)။

Provisioning အမျိုးအစားများ (Types of Provisioning)

Server / Cloud Provisioning

AWS, Google Cloud, DigitalOcean ကဲ့သို့သော Cloud Platform များပေါ်တွင် Virtual Machines (EC2 instances), Kubernetes Clusters (EKS/DOKS) သို့မဟုတ် Bare-metal server များကို အလိုအလျောက် တည်ဆောက်ပေးခြင်း။

Network Provisioning

ဆာဗာများ အချင်းချင်း ဆက်သွယ်နိုင်ရန် Virtual Private Cloud (VPC), Subnets, IP addresses, Firewalls (Security Groups) နှင့် DNS records များကို ဖွဲ့စည်းပေးခြင်း။

Storage Provisioning

Kubernetes အတွင်း သင်တွေ့ကြုံခဲ့ရသလို Database များ သို့မဟုတ် App များအတွက် Persistent Volume (PV), AWS EBS, NFS Server သို့မဟုတ် Object Storage (S3) များကို လိုအပ်သလို သတ်မှတ် ချထားပေးခြင်း (Static/Dynamic Provisioning)။

User / Access Provisioning

ဝန်ထမ်းများ သို့မဟုတ် Pod များအတွက် IAM Roles, ServiceAccounts, RBAC Permissions များကို ထုတ်ပေးခြင်း။

အသုံးအများဆုံး Provisioning Tools များ

Infrastructure as Code (IaC): Terraform, OpenTofu, AWS CloudFormation, Pulumi Configuration Management: Ansible, Chef, Puppet

၂။ Artifact Management ဆိုတာ ဘာလဲ (What is Artifact Management?)

DevOps CI/CD Pipeline တွင် Artifact ဆိုသည်မှာ Source Code (PHP, Java, Go, Dart စသည်) ကို Build လုပ်ပြီးနောက်၊ Compile လုပ်ပြီးနောက် သို့မဟုတ် Test စစ်ဆေးပြီးနောက် ထွက်ပေါ်လာသည့် "Deploy ပြုလုပ်ရန် အသင့်ဖြစ်နေသော အချောထည် Output ဖိုင်များ (Packaged Binaries / Images / Archives)" ကို ခေါ်ဆိုခြင်း ဖြစ်ပါသည်။

ထို့ကြောင့် Artifact Management ဆိုသည်မှာ အဆိုပါ အချောထည် Software Packages များကို လုံခြုံစွာ သိမ်းဆည်းခြင်း၊ ဗားရှင်းနံပါတ်များ တပ်ဆင်၍ သမိုင်းကြောင်း ထိန်းသိမ်းခြင်း (Versioning)၊ Vulnerability စစ်ဆေးခြင်း (Security Scanning) နှင့် Kubernetes သို့မဟုတ် Server များပေါ်သို့ အချိန်မရွေး လှမ်းဆွဲတင်နိုင်အောင် စီမံခန့်ခွဲပေးသည့် စနစ် (Registry) ဖြစ်ပါသည်။

အဓိက Artifact အမျိုးအစားများ (Types of Artifacts)

Container Images

Docker Images / OCI Images (ဥပမာ- `my-app:v1.0.0`, `bitnami/wordpress`)

Package Archives / Charts

Kubernetes Helm Charts (`my-chart-0.1.0.tgz`), Debian Packages (`.deb`), RedHat (`.rpm`)

Compiled Language Binaries

Go compiled binaries, Rust binaries, Java `.jar` / `.war` ဖိုင်များ

Language Dependencies

PHP Composer packages, Node.js NPM `.tgz` packages, Python Wheels (`.whl`)

အသုံးအများဆုံး Artifact Management Tools များ (Registries)

Enterprise Universal Registries: JFrog Artifactory, Sonatype Nexus Cloud Native Registries: Harbor, AWS ECR, Google Artifact Registry, GitHub Packages / GHCR Helm Hubs: Artifact Hub, ChartMuseum

၃။ CI/CD Pipeline ထဲတွင် ၎င်းတို့ (၂) ခု ပေါင်းစပ် အလုပ်လုပ်ပုံ (End-to-End Workflow)

======================= CI (CONTINUOUS INTEGRATION) ======================= [ Developer Git Push ] │ ▼ (GitHub Actions / GitLab CI) [ Compile / Build & Run Automated Tests ] │ ▼ (Build Docker Image & Package Helm Chart) [ Push to ARTIFACT MANAGEMENT ] <==== Store: my-app:v1.2.0 & helm-chart:0.1.0 (Harbor / AWS ECR / Artifactory) (Vulnerability Scanning, Immutable Versioning) ======================= CD (CONTINUOUS DEPLOYMENT) ======================= │ ▼ [ PROVISIONING LAYER ] <==== Terraform creates AWS EKS, VPC, Security Groups (Infrastructure Ready) (or Dynamic Storage Provisioning for PVC) │ ▼ [ Deployment via Helm / Kubectl ] <==== Pulls Docker Image & Helm Chart from Artifact Manager │ ▼ [ Running Kubernetes Cluster ]

၄။ နှိုင်းယှဉ်ချက် အကျဉ်းချုပ် ဇယား (Provisioning vs. Artifact Management)

အချက်အလက် Provisioning Artifact Management
အဓိက တာဝန် ဆာဗာ၊ ကွန်ရက်နှင့် သိုလှောင်မှု အခြေခံအဆောက်အအုံကို တည်ဆောက်ပြင်ဆင်ပေးခြင်း အချောထည် Software Packages နှင့် Container Images များကို သိမ်းဆည်း၊ ဗားရှင်းထိန်းသိမ်းပေးခြင်း
ကိုင်တွယ်သောအရာ Servers, VPC, Subnets, EBS/NFS, IAM Roles, Kubernetes Clusters Docker Images, Helm Charts, `.jar`, `.tar.gz`, Binaries
ပစ်မှတ်နေရာ AWS, GCP, DigitalOcean, Multipass, Hardware Docker Hub, AWS ECR, Harbor, JFrog Artifactory, GHCR
အချိန်ကာလ System Setup ပြုလုပ်ချိန် သို့မဟုတ် Cluster တိုးချဲ့ချိန် (Scale out) Code အသစ်တစ်ခုစီ Build ပြီးတိုင်း (Continuous Delivery)
ဥပမာ ကိရိယာများ Terraform, Ansible, `eksctl`, CloudFormation Docker Registry, Harbor, Nexus, Artifactory

၅။ Senior DevOps & SRE များသာ နားလည်သော အချက်များ (What Only Seniors Understand)

Immutability Principle (မပြောင်းလဲနိုင်သော စည်းကမ်းချက်):

Artifact Management တွင် အရေးကြီးဆုံး စည်းမျဉ်းမှာ "Artifacts must be immutable" ဖြစ်သည်။ ဆိုလိုသည်မှာ Docker image tag `v1.0.0` သို့မဟုတ် Helm chart `0.1.0` ကို Artifact registry ပေါ်သို့ တစ်ကြိမ် Push ပြီးပါက ထို Tag အမည်တူဖြင့် နောက်တစ်ကြိမ် overwrite ထပ်ရေးခွင့်ကို လုံးဝ ပိတ်ထားရပါမည် (Docker tag `latest` ကို Production တွင် လုံးဝ မသုံးရသည့် အကြောင်းရင်း ဖြစ်သည်)။ အကယ်၍ Version တစ်ခုသည် immutable မဖြစ်ပါက Rollback ပြုလုပ်သည့်အခါ ယခင် bug ဟောင်းများ ပြန်ပါလာတတ်ပါသည်။

Golden Images & Baking vs. Runtime Provisioning:

ဆာဗာအသစ်တက်လာတိုင်း `apt update && apt install` စသည်ဖြင့် Provisioning လုပ်ပါက အချိန် ၅ မိနစ်မှ ၁၀ မိနစ်အထိ ကြာမြင့်တတ်သည်။ Senior များသည် Packer ကဲ့သို့ tool များဖြင့် လိုအပ်သော packages အားလုံးကို ကြိုတင် Install လုပ်ထားသည့် AMI/Image (Golden Image) ကို တည်ဆောက်ပြီး Artifact အနေဖြင့် သိမ်းဆည်းထားကြသည်။ ထို့နောက် စက်ဖွင့်သည့်အခါ ထို Image ကို ချက်ချင်း Clone လုပ်ကာ စက္ကန့်ပိုင်းအတွင်း Provisioning ပြီးပြတ်စေပါသည်။

Vulnerability & Compliance Gatekeeper:

ခေတ်သစ် Artifact Manager များ (ဥပမာ Harbor / AWS ECR) တွင် Trivy သို့မဟုတ် Clair ကဲ့သို့ Security Scanner များ ပါဝင်သည်။ Image တစ်ခုထဲတွင် Critical CVE (လုံခြုံရေး အားနည်းချက်) ပါဝင်နေပါက Kubernetes သို့မဟုတ် Production ဆာဗာများက အဆိုပါ Image ကို Pull ဆွဲခွင့် မရအောင် Registry အဆင့်တွင်ပင် ကြားဖြတ် ပိတ်ဆို့ (Quarantine) ပေးနိုင်ပါသည်။

၆။ သတိထားရန်နှင့် အမှားများ (Mistakes to Avoid)

Artifact Registry တွင် Retention Policy (သက်တမ်းသတ်မှတ်ချက်) မထားရှိခြင်း:

CI/CD pipeline က commit တိုင်းအတွက် Docker Image အသစ်များ အဆက်မပြတ် တင်နေပါက ရက်သတ္တပတ် အနည်းငယ်အတွင်း Registry ၏ Disk Space သည် Terabytes ချီ ပြည့်သွားပြီး Bill ကုန်ကျစရိတ် အဆမတန် မြင့်တက်သွားတတ်ပါသည်။ "နောက်ဆုံး Commit ၃၀ သို့မဟုတ် Tagged releases များကိုသာ သိမ်းဆည်းမည်" ဟူသော Auto-cleanup policy ကို မဖြစ်မနေ သတ်မှတ်ရပါမည်။

Configuration Drift in Provisioning:

Terraform ဖြင့် ဆောက်ထားသော Infrastructure ကို အရေးပေါ်ဟုဆိုကာ AWS Console သို့မဟုတ် SSH ထဲမှ လက်ဖြင့် Manual သွားပြင်မိပါက Code နှင့် တကယ့်ဆာဗာကြား မညီမျှမှု (Drift) ဖြစ်ပေါ်ပြီး နောက်တစ်ကြိမ် Pipeline run သည့်အခါ စနစ်များ ပျက်စီးသွားတတ်ပါသည်။ ပြင်ဆင်မှုတိုင်းကို Code မှတစ်ဆင့်သာ Provisioning ပြုလုပ်ရပါမည်။
